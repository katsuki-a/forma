# forma デザインシステム

版: **0.1・デザイン初稿**。方向は [デザインの契約](../spec/0003-design-system.md) に基づく。具体値と見本は実装に向けた定義であり、製品UIの完成・PdMの個別承認を意味しない。

## 木の構造を、共有する情報のかたちに

木を表す中心は、情報の親子関係が読める枝線と階層。深緑をナビゲーションと主要操作に、落ち着いた緑白を作業面に使う。日々の情報を読み書きする面を静かにし、家庭でも仕事でも扱いやすい文字と部品を使う。

木目・森林写真・散らした葉を背景装飾に使わない。大きな宣伝見出し、グラデーション、発光、すりガラス、全領域のカード化、意味のない番号やAIを示すきらめき記号を標準部品にしない。

## 定義元

| ファイル                         | 責務                                 |
| -------------------------------- | ------------------------------------ |
| [tokens.css](tokens.css)         | 色・文字・余白・形状・寸法・動きの値 |
| [components.css](components.css) | 部品の外観と状態、画面幅への適応     |
| [preview.html](preview.html)     | 同じCSSを使う部品の見本と確認用操作  |

数値や色はCSSだけで定義する。以下の説明は値のコピーではなく使い方の契約。見本の起動手順は [READMEのローカル表示](../README.md#ローカルで起動する) を参照する。見本は専用のdev:designコマンドで配信する。アプリ本体も同じCSSを参照する。

## 配色の役割

基本の6色は `palette-forest`（幹）、`palette-leaf`（葉）、`palette-moss`（輪郭）、`palette-mist`（選択面）、`palette-canvas`（背景）、`palette-surface`（作業面）。エラーと注意にだけ別の意味色を用意する。

画面は原則として `color-*` の役割トークンを参照する。主要操作はaction、入力輪郭はborder、背景の区切りはdivider。dividerを入力欄の識別に使わない。深緑の上ではon-darkとfocus-on-darkを使う。ステータスは色に加えて言葉で伝える。

各アプリのテーマを増やす場合も役割トークンを差し替える方式とする。共通の部品寸法、状態、フォーカス、操作名は変えない。基本版は既存パレットの深緑・葉・苔をナビゲーションに適用する。操作や状態の意味は共通である。

## 文字と文言

和文の長文、数字、家族の名前を読みやすくするため、本文と見出しに同じ日本語サンセリフ系統を使う。本文・ラベル・見出しの階層はトークンで固定し、細字や装飾的な英字見出しに依存しない。数字を比較する列は右寄せし、桁の幅を揃える。

現段階のフォントはOSの日本語フォントへのフォールバックを含む。OS間で字形まで一致するとは保証しない。製品の視覚回帰テスト導入時にはフォントファイル・版・ブラウザー・画面幅を固定する。

共通語彙は「アプリ」「項目」「記録」「担当者」「共有する」「下書き」「変更を反映」。利用者に「スキーマ」「ノード」「エンティティ」を操作名として要求しない。将来のAI作成も「会話から作る」のように起こることを示す。家庭では通じない企業前提の略語を使わない。

空状態は次の操作を示す。エラーは対象・理由・修正方法を説明する。「問題が発生しました」だけで終わらせない。保存ボタンと完了表示は同じ動詞を使う。

## レイアウトと階層

広い画面では、左に深緑の構造ナビゲーション、右に一つの主作業面を置く。小さい画面ではナビゲーションを上に置き、作業面を一列にする。これは見本と共通部品の基本適応であり、未採用のモバイル専用機能を追加するものではない。

```text
広い画面                         小さい画面
┌────────┬──────────────────┐   ┌────────────────────┐
│ forma  │ ページ名  主操作   │   │ forma / 構造        │
│ ├アプリ│ 説明・現在の状態   │   ├────────────────────┤
│ │ ├項目├──────────────────┤   │ ページ名 / 主操作   │
│ │ └項目│ 一覧 / 編集フォーム│   │ 一覧                │
│ └アプリ│                  │   │ 編集フォーム        │
└────────┴──────────────────┘   └────────────────────┘
```

本文、見出し、入力ラベルは左揃え。枝線は親子関係のある場所だけで使い、平坦なデータに偽の階層を付けない。アプリと項目の階層をまず扱い、未採用のグループやテーブルを見た目の都合で追加しない。データ一覧は行と列を優先し、各レコードを同じカードへ分割しない。

## 共通部品

| 部品               | 役割と状態                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| 構造ナビゲーション | 入れ子リストと開閉操作。現在位置は背景と太さ、親子関係はインデントと枝線。操作要素はキーボードで到達可能にする |
| ボタン             | 一つの作業領域の主操作を深緑で示す。補助操作は輪郭。削除は言葉と意味色。無効状態は理由も近くに示す             |
| 入力欄             | ラベルを常設し、入力・補足・エラーを同じ並びにする。通常、フォーカス、エラー、無効の状態を揃える               |
| 状態表示           | 状態名を必ず記載する。未着手・進行中・完了の意味を色だけに委ねない                                             |
| 一覧               | 見出し行、左揃えの本文、右揃えの数値、行の区切り。選択とフォーカスを別々に示す                                 |
| 空状態             | 何が未作成かと、次にできる操作を短く示す                                                                       |
| 反映前の確認       | 下書きと利用中の定義を区別し、変更内容と「変更を反映」を示す。初稿の見本は状態表示のみ                         |

角丸は操作部品と面で使い分け、丸いピル形は状態表示だけに用いる。通常の面に影を重ねない。動きは利用者の操作への短い応答に限定し、自動の登場演出を付けない。

## 再現性を維持する変更手順

1. frontend-design系スキルを読み、この主題と既存定義から変更案を作る。新しい主題や別の配色を生成し直さない。
2. 既存の役割・部品で表せるか確認する。必要な変更は定義元に一度だけ加える。
3. 見本に通常・フォーカス・エラー・無効・空状態を反映する。
4. `npm run design:check` で定義済みの色の組み合わせとトークン参照を検査する。デスクトップと狭い画面でも目視する。
5. React実装ではこれらの規則を共通部品に移し、画面は部品を組み合わせる。実装された状態を基準画像とし、以後の変更を比較する。

## アクセシビリティと検証範囲

本文の前景・背景は4.5:1以上、操作を識別する輪郭・フォーカスは3:1以上を設計基準とする。これは [W3Cの文字コントラスト](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) と [非テキストのコントラスト](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) に基づく。対象色の計算成功だけで画面全体の適合を保証しない。

見えるフォーカス、明示的なラベル、エラーとの関連付け、動きを減らす設定への対応を部品に持たせる。「目にやさしい」は見た目の方向であり、医療的な効果を表示しない。
